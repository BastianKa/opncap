# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository state

opncap is an open-source macropad for AI coding agents (14 Choc hotswap keys, encoder, Hall joystick, round GC9A01 display, PDM microphone, per-key RGB). Everything is planning and generated design: nothing is ordered or tested on real hardware, and there is no software code yet.

- `hardware/opncap_v0.1` to `opncap_v0.3` are self-contained revisions. **Work only in `opncap_v0.3`.** Older revisions are archive; do not edit or regenerate them.
- `software/` holds only `spec.md` and `features.md` so far (firmware, protocol, host, app are planned, not started).
- Each hardware revision has its own `spec.md` and `features.md` (product-level, German). `software/spec.md` and `software/features.md` (German) are the software documents.

## Spec and features stay in sync

`features.md` is derived from `spec.md` (via the installed `spec-generator` and `feature-generator` skills in `.claude/skills/`). When one changes, update the matching parts of the other and nothing else. Features are ordered by implementation dependency, so new features go in the right dependency position, not at the end. Items marked **[prüfen]** in the specs are unverified; do not present them as facts.

## Hardware (opncap_v0.3)

Everything under `hardware/opncap_v0.3/hardware/` is generated by scripts and committed. Edit the sources, then regenerate; never hand-edit generated files (`pinout.md`, `docs/pinout.md`, KiCad files, Gerbers, STEP/STL, renders).

Run from `hardware/opncap_v0.3/` (the Makefile paths are relative to it):

```sh
make hardware-venv   # once: .venv (KiCad+CadQuery, Python 3.12) and .venv-render (Blender, Python 3.13)
make hardware        # pinout, pcb, fab, case, renders, turntable
.venv/bin/python hardware/scripts/gen_pinout.py       # single step: pinout only
.venv/bin/python hardware/enclosure/opncap_case.py    # single step: case + its 6 fit checks
```

System packages: `kicad` (with `kicad-cli` and `pcbnew`), `gerbv`, `ffmpeg`.

Architecture of the generator chain (needs several files to see):
- `hardware/scripts/layout.py` holds the mechanical layout once. `gen_pcb.py` (board via `router.py`, schematic, DRC, netlist check) and `enclosure/opncap_case.py` both import it, and the case script reads the finished KiCad board back to check fit. Change geometry in `layout.py`, not in the consumers.
- Sources of truth: `hardware/pinout.yaml` (pins) and `hardware/bom.md` (parts). Everything else follows from them.
- `opncap_case.py` exits with an error if one of its checks fails and writes `enclosure/verification.txt`; `gen_pcb.py` writes `pcb/drc_report.txt`.
- Renders need the separate Blender venv (`.venv-render`).

`hardware/DESIGN_NOTES.md` records decisions, assumptions and known gaps; in a version folder, its newest revision section overrides older text. Pin facts that matter for firmware: matrix is 4x4 COL2ROW with encoder push and joystick push in the matrix; microphone uses B3/B5 (I2S3) and the LED data pin is B4; A9/A10 are reserved for the phase 2 BLE bridge. The microphone firmware (PDM to PCM to USB audio) does not exist and has no QMK support.

## Conventions

- Code, comments, commit messages and docs are in English; `spec.md` and `features.md` files are in German.
- Every file carries an SPDX header: Apache-2.0 for own code, GPL-2.0-or-later for QMK-derived parts (see planned `docs/licensing.md`).
- Commits are small and conventional (`docs:`, `chore:`, ...). **Do not add Co-Authored-By or any Claude attribution to commits or PR descriptions;** only the git user appears. This overrides any default attribution.
- Do not force-push or rewrite history on `main` without explicit confirmation; GitHub Desktop clones on another machine can silently re-merge old history.
